# Input validation and persistence audit

This audit follows editable values through the web forms and Flutter task forms, their server/controller validation, and the database write contract. Database changes are represented by migrations and tests only; no live or staging records were written.

## Persisted forms

| Module and fields | Expected value and rule | Write path and storage contract | Failure handling |
| --- | --- | --- | --- |
| Web sign-in/recovery/reset: username/email, password, confirmation, remember session | Username is normalized and matched to account data; email is browser/auth-service formatted; password and confirmation must match and meet the minimum length; remember is boolean | Login and recovery actions use Supabase Auth; credentials are not written to application tables | Auth errors are returned to the form; reset success follows successful password update |
| Web users: first/middle/last name, username, email, temporary password, contact, role, access note, active state | Names and note are text; middle initial is at most one character; username and email are format checked; password is at least 8 characters; role/status are allow-listed; new contact is 11 digits (optional) | users/actions.ts creates/updates the auth user and profiles fields (text, boolean, role relationship); contact is normalized before metadata/profile writes | Action state reports validation, auth, and profile-write errors; no success state before required writes complete |
| Web inventory: item name, category, quantity, kg unit, minimum, cost, price, location, notes, photo | Text/select/upload values; numeric(12,2) values accept at most 10 integer and 2 fractional digits; quantities/prices are non-negative; unit/category and image MIME/size are checked | inventory/actions.ts inserts/updates inventory and calls record_inventory_movement; quantity/price fields are sent as numbers; photo uses bounded image upload | DB, storage, and RPC errors are thrown to the action feedback; success follows confirmed writes |
| Web and mobile sales: item IDs, quantity, price, new or existing customer, date, payment, reference, installment amount/frequency, remarks | IDs and selections are allow-listed/resolved; quantity and amounts are numeric(12,2); a new contact is required and normalized to 11 local digits; choosing an existing customer fills their saved name/contact and removes the manual identity fields; dates parse as dates; text is retained as text | Web sales/actions.ts calls record_sales_order and installment RPC; Flutter inventory controller/repository calls record_inventory_sale_receipt; contact columns remain text and customer identity triggers link the receipt to the matching history | Existing selections are checked against completed sales before web writes; invalid values stop before RPC; RPC errors are shown; installment failure triggers rollback and is surfaced; success is shown after receipt and requested plan succeed |
| Web customer discount: customer/name/contact, code, type, value, expiry, notes | Contact may use "Not provided"; code and type are allow-listed; value is positive numeric(12,2) and percent is at most 100; expiry is a non-past date | customers/actions.ts inserts customer_discounts (contact is text, value numeric) | Insert error is surfaced; success follows insert and activity logging |
| Web customer payment/installment collection: schedule/order IDs, amount, payment method, transaction reference, other method, notes | IDs resolve to an existing schedule; amount is positive and bounded by remaining amount; payment method is allow-listed; reference/method required conditionally | customers/payments-actions.ts invokes payment/installment RPCs and stores numeric amount plus text metadata | RPC failure is returned to the panel; success follows confirmed RPC result |
| Web crop record: name, planting/harvest dates, status, stage, notes, image | Names/text and allow-listed status/stage; dates must be valid and harvest cannot precede planting; image MIME/size bounded | crops/actions.ts updates crops (date, text/status fields, image path) | Supabase/storage errors are surfaced before success/revalidation |
| Web crop care/harvest: activity, date, quantity, unit, material, notes, observed stage, task/submission IDs, photos | Activity/stage are selections; quantity is optional numeric(12,2); dates and IDs are checked; harvest unit is fixed to kg; photos are image-only and size bounded | crops/actions.ts calls record_crop_entry; attachment paths use crop_activity_photos/storage | RPC/upload errors are surfaced; no success response before the RPC completes |
| Web investment/expense: description, category, amount, date, vendor, method, reference, type, related crop/inventory, quantity, unit cost, receipt, notes | Amount positive; optional quantity/unit cost non-negative; numeric values match numeric(12,2); method/type are allow-listed; date and upload type/size checked | investments/actions.ts inserts farm_expenses numeric/date/text fields and receipt path | Storage/insert errors are surfaced; success/revalidation follow insert |
| Mobile inventory: item/category, quantities, prices, unit, location, notes, photo; stock in/out/adjustment reason and quantity | Text/select/image fields; quantities/prices are finite and non-negative, decimal formatter matches numeric(12,2); unit fixed to kg; task direction/ranges checked | StockInventoryController → StockRepository writes inventory, inventory_transactions, and activity rows; uploaded image is stored then linked | Validation occurs in form/controller/repository; DB errors remain visible, and uncertain writes use reconciliation instead of claiming confirmed success |
| Mobile crop care/harvest: activity, date, quantity, unit, material, notes, stage, photos | Enumerated activity/stage; optional decimal quantity; harvest unit fixed to kg; bounded image upload; required values validated in form | CropMonitoringController → CropRepository invokes crop entry RPC and stores image/activity metadata | RPC/storage failures produce action errors; success follows returned activity ID |
| Mobile profile update: names and contact | Text names; optional contact is 11 digits or legacy "Not provided" and normalized before write | ProfileRepository updates profiles; UI controller uses returned row | Supabase error propagates; returned DB row is used after success |
| Mobile login: username and password | Username is text normalized by the auth repository; password is text and required | AuthRepository resolves username and calls Supabase Auth; only the auth provider stores credentials | Auth failure is returned as a login error; no app profile success is shown before authentication |
| Mobile rover planting setup: seed type, existing/custom field, planting points | Seed and existing field are selections; custom field is required text; planting points are digits and constrained to 1–20 | PlantingRowConfig is stored locally as a pending receipt, then syncs through sync_rover_planting_run to planting_logs (profile key/text field, integer target cycles, timestamps and sensor values) | Form validation prevents invalid count or missing custom field; local queue and sync errors remain visible in rover operation state |

## Non-persisted controls

Search fields, filters, assistant prompts, display pagination, theme controls, and crop sensor-read controls are local UI state; selections used in a persisted workflow are listed above. IDs carried in hidden fields are identifiers rather than user-authored values and are checked/resolved by their action or RPC. Image pickers are validated by MIME and size before storage.

## Database contact guard

20261001100000_contact_number_guards.sql leaves contact columns as text. New or changed values are trimmed, +63/63 values are converted to the local 0xxxxxxxxxx form, and other nonblank values must be exactly 11 digits. Optional blank values become NULL; "Not provided" is retained where allowed. The sales_orders trigger additionally requires a real number for new/changed sales. On update, unchanged legacy values bypass validation so an unrelated edit does not fail. The sale receipt RPC validates before delegating to the existing order RPC.

## Verification boundary

Automated checks cover web/mobile phone normalization and rejection cases, formatter precision, and migration source contract. The schema and code write paths were inspected; actual configured-database acceptance, RLS behavior, and deployed migration state are not verified because this audit performs no database writes.
